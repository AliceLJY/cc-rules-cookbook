# Memory Architecture

**Three-dimensional memory system for AI agents that persists knowledge across sessions.**

---

## The Problem

Each Claude Code session starts with a blank slate. Knowledge accumulated in previous sessions -- decisions made, bugs found, preferences learned, workflows established -- is lost unless explicitly persisted.

Local files (CLAUDE.md, memory directories) solve the storage problem. But storage without organization is a junk drawer. You need structure.

---

## The Three Dimensions

Memory items are ranked on three dimensions:

### 1. Recency

When was this memory created or last accessed?

Recent memories are more likely to be relevant to the current session. But recency alone is insufficient -- a critical architectural decision from three months ago outranks a log message from yesterday.

### 2. Relevance

How closely does this memory match the current context?

Determined by keyword matching, semantic similarity, or explicit tagging. A memory about "database migration" is highly relevant when the current task involves schema changes.

### 3. Importance

How consequential is this information?

| Level | Examples |
|-------|---------|
| **High** | Architecture decisions, breaking change records, security-sensitive configurations, user preferences that affect all sessions |
| **Medium** | Implementation details, debugging findings, project-specific conventions |
| **Low** | Session logs, routine task completions, temporary workarounds |

Importance is the tiebreaker. When two memories are equally recent and equally relevant, importance determines which one surfaces.

---

## Dual-Write Strategy

Write memories to two locations:

1. **Local files**: `~/.claude/` directory structure, CLAUDE.md, project-specific memory files
2. **External memory service**: A dedicated memory system (database, API, or MCP tool)

**Why dual-write?**

- Local files are fast and always available but not searchable across projects
- External services are searchable but may be unavailable (network, service down)
- If one fails, the other succeeds -- no memory is lost

**Rules**:
- External service failure does not block local saves
- Local file write is always the primary operation
- External service is enhancement, not requirement

---

## Compact Priorities

When memory storage reaches capacity or context windows fill up, compact according to these priorities (highest priority = keep, lowest priority = discard):

| Priority | Content Type | Rationale |
|----------|-------------|-----------|
| 1 (Keep) | Architecture decisions | Expensive to re-derive, affect everything downstream |
| 2 | Modified files and their purpose | Essential for continuity |
| 3 | Verification status | Prevents re-testing or shipping untested code |
| 4 | Open TODOs and blockers | Prevents work from being silently dropped |
| 5 (Discard first) | Raw tool outputs | Can be regenerated by re-running the tool |

## Memory File Organization

```
~/.claude/
├── CLAUDE.md              # Index file -- points to specialized files
├── projects/
│   └── {project}/
│       ├── MEMORY.md      # Project-specific memory index
│       └── *.md           # Specialized topic files
└── memory/
    ├── identity.md        # User profile and preferences
    ├── goals.md           # Long-term objectives
    ├── feedback-index.md  # Behavior corrections (indexed)
    └── project-index.md   # Project references (indexed)
```

**Key principle**: CLAUDE.md is an index, not a dump. It points to specialized files. Each specialized file covers one topic. When a topic grows too large, split it.

---

## Memory Lifecycle

```
New information → Assess importance (high/medium/low)
                       ↓
              Dual-write (local + external)
                       ↓
              Index in CLAUDE.md or MEMORY.md
                       ↓
              (Over time) Compact:
              - Merge related low-importance items
              - Archive obsolete items
              - Keep high-importance items indefinitely
```

---

## Anti-Patterns

### The Memory Dump

Writing everything to CLAUDE.md. The file grows to thousands of lines, the AI skims it, and important rules get buried under session logs.

**Fix**: CLAUDE.md is an index. Details go in specialized files.

### The Blind Read

Reading all memory files at session start. This fills context with irrelevant information and degrades performance.

**Fix**: Check the index first, then open only the files relevant to the current task.

### The Orphaned Memory

Writing a memory file but not adding it to the index. Future sessions don't know it exists.

**Fix**: Every memory file must be referenced from CLAUDE.md or MEMORY.md.

### The Stale Memory

Keeping outdated information (deprecated APIs, old file paths, resolved TODOs) in memory files.

**Fix**: During compaction, actively remove information that's no longer true.

---

## Implementation

Add to your `CLAUDE.md`:

```markdown
## Memory Rules

- CLAUDE.md is an index — details in specialized files
- Check index first, then open specific files (never read all blindly)
- New knowledge → write to specialized file + update index
- Dual-write: local files + external memory service
- Compact: architecture decisions > modified files > verification > TODOs > tool output
```
